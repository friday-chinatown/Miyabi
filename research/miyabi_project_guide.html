Miyabiとは？

Miyabi（雅）は、あなたの代わりにプログラミングをしてくれるAIシステムです。

普通のソフトウェア開発では、エンジニアがコードを書いて、テストして、レビューして、サーバーにアップロード（デプロイ）します。 Miyabiを使うと、これらの作業を⚡ 全部AIが自動でやってくれます。

💡 わかりやすいたとえ

レストランに例えると...
あなたは「カレーが食べたい」とメニューに書くだけ（= Issue作成）。
すると、料理長（CoordinatorAgent）が指示を出し、
調理担当（CodeGenAgent）が料理を作り、
味見係（ReviewAgent）が品質をチェックし、
配膳係（DeploymentAgent）がテーブルに届けてくれます。
あなたは注文するだけ。あとは全自動。

Windows 95がパソコンを、iPhoneがスマホを「誰でも使えるもの」に変えたように、
MiyabiはAI開発を🌱 誰でも使えるものに変えます。

⚖️ 自律の三法則

MiyabiのすべてのAIエージェントは、この3つの法則に従って動きます。
これはAIが「暴走」しないためのルールブックです。

01
📊

第一法則

客観性の法則（Objectivity）

AIは「なんとなく」で判断しません。すべての判断はデータと数字に基づいて行います。 感情や気分に左右されず、常に冷静に数字で評価します。

👉 具体的には
コードの品質を0〜100点で採点し、80点以上でないと合格にしません。 「なんとなく良さそう」ではなく「87点だから合格」と判断します。
02
⚡

第二法則

自給自足の法則（Self-Sufficiency）

AIはできるだけ人間に頼らず、自分で問題を解決します。 失敗しても最大3回自動でやり直し、本当にダメなときだけ人間に助けを求めます。

👉 具体的には
人間が介入する割合を5%以下に抑えることが目標。 コードが不合格なら自動で修正を試み、3回やり直してもダメな場合だけ人間にエスカレーションします。
03
📝

第三法則

追跡可能性の法則（Traceability）

AIのすべての行動は記録に残ります。 何をしたか、なぜそうしたかが全部GitHubに記録されるので、後から確認できます。

👉 具体的には
すべてのログは .ai/logs/ に日付ごとに保存。 AIの判断理由もIssueのコメントに記録。「ブラックボックス」にはなりません。

📜

言語とランタイム

Miyabiは主にTypeScriptで書かれています。TypeScriptは「型」があるJavaScriptで、間違いを事前に防げます。

  • TypeScript Strict モード / ES2022
  • Node.js v18+ ランタイム
  • pnpm 9 パッケージ管理
  • Python コンテキスト最適化用
🤖

AI / エージェント基盤

AIの頭脳であるClaude APIと、エージェント間の通信プロトコルMCPが核心技術です。

  • Anthropic SDK Claude Sonnet 4
  • MCP SDK 172+ 統合ツール
  • Agent Skill Bus 110+ スキル
🐙

GitHub統合

GitHubのAPIを使って、Issue、PR、Projects、Actionsを自動操作します。

  • Octokit REST GitHub REST API
  • Octokit GraphQL 高度なクエリ
  • Actions 16+ ワークフロー
  • Webhooks リアルタイム連携
✅

テスト / 品質管理

コードの品質を自動で保証する仕組み。テスト、型チェック、コード規約を自動実行します。

  • Vitest ユニット / 統合テスト
  • Playwright E2E ブラウザテスト
  • ESLint コード規約チェック
  • TypeScript 型安全性検証
💻

CLI / ユーザーインターフェース

インフラ / DevOps

🐳 Docker & デプロイ

Dockerは「アプリの箱詰め技術」です。Miyabiはマルチステージビルドという技術で、 軽くて安全なコンテナを作成します。まるでロシアの入れ子人形（マトリョーシカ）のように、必要なものだけを最終形に残します。

💡
Dockerとは？ アプリを動かすために必要なもの（コード、ライブラリ、設定）を全部まとめて「箱（コンテナ）」に入れる技術です。 この箱さえあれば、どのサーバーでも同じように動きます。「引っ越し用の段ボール」のようなものです。

マルチステージビルド（4段階）

📥
Stage 1: base

土台づくり。Alpine Linux（軽量OS）にgitやSSHなど基本ツールをインストール。

node:20-alpine
📦
Stage 2: deps

本番に必要なライブラリだけをインストール。開発用ツールは含めない。

pnpm 9 / production deps only
🔨
Stage 3: builder

全ライブラリをインストールしてTypeScriptをコンパイル（翻訳）。ビルド完了後は不要に。

全deps + TypeScriptビルド
🚀
Stage 4: runtime（最終形）

実行に必要な成果物だけを集めた最終コンテナ。非rootユーザーで安全に実行。

非rootユーザー(miyabi:1001) / 最小構成
🎯
なぜ4段階もあるの？ 料理に例えると：材料を買う(base) → 必要な調味料を並べる(deps) → 料理する(builder) → 盛り付けて提供する(runtime)。 最終的にお客様に出すのは「盛り付けた料理」だけ。鍋やまな板は不要なので含めません。これによりコンテナが軽くて安全になります。

各状態のかんたん説明

📝 draft

タスクが作られたばかり。まだ誰にも割り当てられていない状態です。

⏳ pending

実行の順番を待っている状態。キューに入っています。

🔍 analyzing

Issue Agent が Issue を分析中。ラベル付けと複雑度評価をしています。

🔨 implementing

CodeGen Agent がコードを書いている最中です。

📋 reviewing

Review Agent がコードを 100 点満点で採点中。80 点未満なら差し戻し。

🚀 deploying

本番環境にコードを配置中。テスト → ビルド → デプロイ → ヘルスチェック。

✅ done

全工程が完了。Issue がクローズされ、PR がマージされます。

🛑 blocked

他のタスクや外部要因で先に進めない状態です。

❌ failed

処理が失敗しました。pending に戻ってリトライできます。

🚫 cancelled

タスクが取り消されました。draft に戻して復活も可能。

データモデル

Miyabi のシステムで使われる主要なデータの型（かた）を紹介します。それぞれがどうつながっているかを見てみましょう。

📋 ManagedTask

interface -- タスクの全情報
  • currentState -- 今の状態（10 種類）
  • type -- タスクの種類（7 種類）
  • priority -- 優先度
  • assignedAgent -- 担当エージェント
  • retryCount -- リトライ回数
  • stateHistory -- 状態変更の履歴
  • githubIssueNumber -- 紐付く Issue 番号
→ BaseTask を拡張

🤖 AgentType

type -- エージェントの種類
  • coordinator -- 司令塔
  • codegen -- コード生成
  • review -- レビュー
  • issue -- Issue 分析
  • pr -- PR 管理
  • deployment -- デプロイ
  • test -- テスト
→ ManagedTask が参照

📨 AgentMessage

interface -- エージェント間の手紙
  • from -- 送信元エージェント
  • to -- 送信先エージェント
  • type -- メッセージの種類（8 種）
  • priority -- 優先度（0-3）
  • payload -- メッセージ本文
  • ttl -- 有効期限（ミリ秒）
→ AgentType を使用

📊 ExecutionResult

interface -- 実行結果の記録
  • taskId -- タスク ID
  • success -- 成功したか
  • state -- 実行後の状態
  • durationMs -- 所要時間
  • agentType -- 実行したエージェント
  • artifacts -- 成果物のリスト
→ ManagedTask から生成

interface -- タスク依存関係の地図

  • edges -- タスク間のつながり
  • levels -- 並列実行できるグループ
  • criticalPath -- 最長経路

  • nodes -- ノード（エージェント等）
  • edges -- ノード間の接続
  • createdAt -- 作成日時
